# 기술 결정 기록

선택한 이유와 포기한 것을 함께 남깁니다. 아직 측정하지 않은 항목은 그렇다고 적었습니다.

## 1. 비동기 IO: standalone Asio (IOCP 직접 구현은 샘플로만)

- **선택 이유**
  - 이 프로젝트가 보여 주려는 것은 서버 권위 구조(M3 동기화, M4 스킬 검증)이고, IO 계층은 그 기반입니다. IOCP 직접 구현은 버퍼 수명과 종료 처리에 시간이 크게 들어 M3 이후 일정을 위협합니다.
  - Asio는 Windows에서 IOCP, Linux에서 epoll로 동작해서 같은 코드가 두 OS에서 빌드됩니다. CI도 Linux/Windows에서 같은 테스트를 돌립니다.
- **포기한 것**: IOCP를 직접 다루며 얻는 저수준 경험. 이를 보완하려고 `samples/iocp-echo`(에코 서버)를 따로 만들었고, CI의 Windows 러너에서 실제로 실행합니다.
- **스레드 모델**: `io_context` 1개와 스레드 1개로 시작했습니다. 모든 핸들러가 순차 실행되어 세션·방 상태에 잠금이 필요 없고, 방 단위 로직(M3)을 단순하게 유지할 수 있습니다. 부하 측정(M5) 결과에 따라 스레드와 strand를 추가할 계획이며, 현재 구조는 `Session`이 상태를 직접 들고 있어서 그때 방 단위 strand로 옮겨야 합니다.
- **콜백 스타일**: C++20 코루틴 대신 콜백(Proactor)을 씁니다. 컴파일러 버전(특히 MSVC)에 덜 민감하고, 완료 핸들러가 `shared_from_this`로 수명을 잡는 패턴이 IOCP 모델과 대응됩니다.

## 2. 직렬화: protobuf (FlatBuffers는 보류)

- **선택 이유**
  - 필드 번호 기반이라 필드를 추가해도 이전 클라이언트와 호환됩니다 (M3 이후 패킷이 늘어날 때 유리).
  - C++과 C# 코드 생성기가 모두 성숙하고, 같은 버전(3.21.12)의 서버/클라 런타임을 맞출 수 있습니다.
  - 파싱 실패가 명확해서 "잘못된 패킷 → 연결 종료" 정책을 구현하기 쉽습니다.
- **포기한 것**: FlatBuffers의 zero-copy 읽기. 파싱 비용 차이는 **측정하지 않았습니다.** 현재 패킷은 작고 빈도가 낮아서 병목이 될 가능성은 낮지만, 이동 동기화(M3) 패킷이 많아지면 M5에서 측정해서 다시 판단합니다.
- **C++은 lite 런타임**: reflection이 필요 없어서 `optimize_for = LITE_RUNTIME`을 사용합니다 (빌드와 바이너리가 가벼움). C# 생성기는 이 옵션을 무시합니다.
- **버전 고정(3.21.12)**: abseil에 의존하지 않는 마지막 계열이라 소스 빌드가 가볍습니다. 대신 최신 기능은 쓸 수 없습니다.

## 3. 의존성: CMake FetchContent (vcpkg/Conan 미사용)

- **이유**: `git clone` 후 CMake만 있으면 어느 PC에서든 바로 빌드됩니다. 개발 환경(Visual Studio 버전 등)에 영향을 덜 받습니다.
- **비용**: 처음 설정할 때 Asio와 protobuf 소스를 받아 컴파일해서 시간이 걸립니다 (Linux 4코어 기준 protobuf 빌드 약 1분 15초).
- **보완**: 오프라인이면 `-DFETCHCONTENT_SOURCE_DIR_ASIO`, `-DFETCHCONTENT_SOURCE_DIR_PROTOBUF`로 로컬 소스를 지정할 수 있습니다.

## 4. 프레이밍: 길이(u16) + 타입(u16) 헤더

- 구현이 단순하고 디버깅하기 쉽습니다 (`docs/protocol.md`의 hex 예시 참고).
- payload 상한(4096)을 두어 잘못된 길이로 메모리를 소진시키는 것을 막습니다. 이동 동기화 패킷은 이보다 훨씬 작을 것으로 예상합니다.
- 버전 필드와 체크섬은 넣지 않았습니다. 프로토콜 버전 협상은 범위 밖입니다.

## 5. 잘못된 패킷: "해석 불가는 끊고, 값 오류는 응답"

`docs/protocol.md`의 6장 참고. 해석할 수 없는 데이터 뒤의 스트림은 신뢰할 수 없어서 연결을 끊고, 정상 클라이언트도 낼 수 있는 값 오류는 오류 코드로 알립니다.

## 6. 검증 방식

- 통합 테스트(`tools/`)는 서버 프로세스를 직접 띄우고 TCP로 검증합니다. protobuf 라이브러리 없이 와이어 형식을 직접 인코딩해서 서버 구현과 독립적으로 형식을 확인합니다.
- 테스트가 실제로 결함을 잡는지 확인하려고 서버 로직을 일부러 망가뜨려(방 정원 값, 닉네임 해제 누락, 검증 생략, 파싱 실패 무시) 해당 테스트가 실패하는지 확인했습니다.
- ASan/UBSan 빌드로 같은 테스트를 돌려 수명 문제와 정의되지 않은 동작을 점검했고, 이 과정에서 빈 payload를 `nullptr`로 파서에 넘기는 문제를 찾아 고쳤습니다.
